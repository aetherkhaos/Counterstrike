# L2.13 Web-to-SQL — Instructor Hint Sheet (Progressive Release Only)

**Use:** Guiding hints for teams that are stuck, released one phase at a
time, only to teams that need them. **Do not distribute this document to
students** and do not reveal a hint before a team has made a genuine attempt
at the corresponding phase.

**Companion docs:**

- [`student-brief.md`](student-brief.md) — given to students at lab start.
- [`instructor-guide.md`](instructor-guide.md) — facilitation SoT (opening,
  timing, progressive hint release).
- [`answer-key.md`](answer-key.md) — full discovery-to-root walkthrough
  (exact commands, payloads, credentials, exploit code).

## How to Use This

- Withhold by default. The lab is designed to be solvable from the Student
  Brief's operational context and standard recon methodology alone.
- If a team stalls on a phase for an extended period (instructor's
  judgment — e.g., 15–20 minutes with no forward progress), share only the
  hint matching where they're stuck.
- Reveal hints **in order**; do not skip ahead even if a team asks about a
  later phase.
- These are directional hints, not exact syntax. If a team needs exact
  commands, point them back at their own evidence and tool documentation —
  do not hand them lines from the Instructor Guide. **Exception:** after
  the second flag, when they come to you because a needed compile tool is
  missing, you may give the `docker load` / `docker run` compile lines in
  phase 8. Do not dump the rest of the answer key.

## Phase Hints

1. **Recon the web tier.** Identify what services the target exposes and how
   its application authenticates users.
2. **Test the authentication mechanism.** Determine whether the login logic
   can be bypassed through injection-based testing. If you get a database
   error back, that error is telling you something — read it carefully
   before trying another payload.
3. **Expand access.** Once authenticated, look for additional attack surface
   inside the application that could lead to code execution on the host —
   check for anywhere the app lets you upload something.
4. **Enumerate the foothold — first flag.** With code execution, look for
   configuration data that might point to additional infrastructure or
   stored credentials. The web-tier flag should be reachable from here.
5. **Determine reachability.** Check whether anything you found is directly
   reachable from your attacker position. If not, use a pivot/tunnel
   technique to reach it through the host you already control.
6. **Access the new tier.** Use what you've discovered to authenticate to
   the newly reached system, and determine what level of access that account
   actually has.
7. **Escalate if needed.** If your access on that tier is not already
   privileged, look for another credential you may have already collected
   but not yet tried, before assuming you need an exploit.
8. **Service-account shell — second flag.** Once they have a host shell as
   the database service account, look for proof of access in that account's
   native directories. That file may also tell them to speak with the
   instructor if the next step needs something that is not on this host.

   **When they come to you after the second flag:** The SQL host has no
   `gcc`, and this range has no internet (`apt-get` and Docker Hub pulls
   will fail). A compile image is already on the ops/Kali box. Walk them
   through load and compile only; they still write their own source and
   finish the LPE themselves.

   ```bash
   ls /opt/docker-gcc
   docker load -i /opt/docker-gcc/pwnkit-gcc-12.04.tar.gz
   docker images
   ```

   `docker images` should show `pwnkit-gcc:12.04`. Then compile inside that
   image (old glibc, current directory bind-mounted):

   ```bash
   docker run --rm -v "$PWD":/tmp -w /tmp pwnkit-gcc:12.04 \
     gcc -shared -o pwnkit.so pwnkit.c -fPIC
   ```

   If `docker run` tries to pull, the image was not loaded. Stop here. Do
   not give PwnKit source, the Python driver, or how to deliver the
   exploit.
9. **Local privilege escalation — third flag.** If you have a shell but not
   root, enumerate the host broadly for a viable escalation path (don't
   jump straight to a specific exploit name). The root flag should only be
   reachable at the highest privilege level.
10. **Document the chain.** Record every transition — entry vector,
    credentials, pivot points, and final privilege level obtained on each
    tier — clearly enough that a teammate could follow your logic without you
    in the room.
