# Lab L4.0.a Alternative — Reconstruct the Adversary Exfil Receiver and Rehearse SOM

## Student Brief

**Phase:** Week 4 opening block (mission prep).  
**Duration:** Instructor-flexible (individual build + rehearsal).  
**Platform:** Shared vSphere / vCenter — see [../../../../environments/effects_lab_env/vsphere/README.md](../../../../environments/effects_lab_env/vsphere/README.md).  
**Relationship to L4.0.a:** This is an **instructor-assigned parallel option**, not a replacement and not a follow-on. Complete **this** brief **or** the document-pipeline L4.0.a brief — not both unless the instructor directs otherwise.

## Operational Context

You are preparing a notional counterstrike mission against the same adversary
collection path you already hunted in **Week 1 and Week 3 group activities**.
Before live execution, build a **threat-representative** slice of the
**software stack the adversary used to receive stolen files**, then **rehearse**
whether the captured collection/exfiltration client still lands files on
terrain **you** control.

**Non-goal:** Recreating the full victim enterprise, every workstation, the
complete redirector farm, or a gold-image clone of range hosts you already
saw.

**Goal:** Identify and instantiate only the **critical OE elements likely to
impact that receive path**, then prove — through the **actual client
contract you already recovered** — that a file can be accepted, stored, and
observed. Document what you could not reproduce and how that bounds the
result.

This lab uses a **different** scenario from the lecture redirector example
and from the other L4.0.a document-pipeline brief. Apply the same decision
process: match what can flip the result, compromise what does not, and
document bounds so results are not over-read.

## Access (Ops Station → Build Environment)

## Notional Mission Package (FRAGO)

### Situation

During Week 1 and Week 3 group work you already recovered the adversary’s
**collection/exfiltration client** and associated evidence (script content,
configuration values, destination clues, authentication artifacts, and any
notes from live hosts you surveyed). That client is the **source of truth**
for this rehearsal. This brief will **not** restate those details.

Command needs a **threat-representative receiver** you control so operators
can rehearse delivery, observe what lands, and later support
**reconnoiter / degrade / disrupt** options against the adversary’s
ability to collect (CG/CV logic from Week 1). Pair rehearsed TTPs with
**ATT&CK** technique IDs; note **ENGAGE** / **D3FEND** language you would
use with blue-space partners.

You **cannot** treat a screenshot from the original range as proof that
**your** stack works. You must instantiate the receive path and exercise
the **same client contract** against addresses **inside your `/29`**.

Collection also indicates (from **your** prior work — confirm in your
notes, do not invent from this paragraph):

- Stolen files leave the victim terrain through an automated client, not
  through an interactive operator paste.
- The client authenticates and uploads using values recovered from the
  script / related artifacts.
- Destination identity, listen port, API shape, and backend dependencies
  were discoverable on the live range and in recovered files.
- Exact product build, runtime libraries, persistence method, and disk
  layout are only **partially known** unless your notes recorded them.
  Those unknowns are rehearsal variables.

**Client vs operator split:** the captured client is the background/load
and the **success oracle**. **You** build and operate the receiver. Copying
a file onto the receiver with `scp` / console drag-and-drop rehearses a
different TTP.

### Mission

**Reconnoiter** the receive path well enough to rebuild the load-bearing
pieces, then determine whether the captured client can still support later
effects against the adversary’s collection capability.

Prove, through the **actual recovered client path**:

1. The reconstructed stack accepts an upload that matches the recovered
   client contract (method, target, authentication, and file+message
   fields you observed).
2. The landed object is observable on the receiver (UI, API, datastore, or
   equivalent native evidence — record which).
3. Which recovered values had to be **retargeted or regenerated** for a
   stack **you** built, and why.
4. Which conditions make the receive path succeed, degrade, or fail.

### Access constraint (mission, not vSphere)

Mission success is **captured-client upload into the receiver you built**.
Do not add an interactive admin session on the receiver “to place the
file” and then claim that as SOM proof. Admin access for **install and
debug** is expected; the **graded rehearsal** is the client contract.

### Friendly constraint

Shared cluster; no egress for ISO or package download; stay in your IP
block; preserve enough RAM for later tool testing (L4.0.b). Classroom
resource caps are a training constraint — operational ceilings will
differ. Document what you could not reproduce.

If your retained Week 1 / Week 3 evidence is incomplete, **do not ask the
instructor to fill in destination product, credentials, or API details.**
Re-collect from notes, screenshots, exports, or live range access you
already hold if that access is still in scope. If a gap remains, document
it, derive a **defensible substitute**, test it, and bound the claim.

## Specific Tasks

1. **Evidence inventory:** From artifacts **you already collected** in Week
   1 and Week 3 group activities, list the destination clues that change a
   build decision (protocol, listen behavior, authentication, upload
   fields, host/OS hints, persistence, dependencies). Cite the source for
   each item (script variable, file path, process/service, config, note).
   Name what you do **not** know.
2. **OE selection:** Keep only those OE elements that change whether the
   captured client can land a file. Write one sentence of rationale per
   kept element, and name what you will **not** build (victim file share,
   golden-ticket path, full redirector web stack, extra C2, and so on —
   unless your evidence shows that piece is load-bearing for the receive
   contract).
3. **Build:** Deploy **blank** guests in vSphere under your folder. Install
   and configure the kept elements. Stay inside the RAM cap and your
   static `/29`. Retarget every recovered destination address to **your**
   block; do not aim at the original range IPs.
4. **Client rehearsal:** Exercise the captured collection/exfiltration
   client (or a minimal replay you derived **from that client** after
   inspecting it) so it uploads into **your** receiver. Inspect before you
   run. Record every value you changed and why the original recovered
   value could not be used unchanged.
5. **Document live state:** Network diagram (roles + addresses), host/role
   + RAM table, snapshot plan (at least one pre-rehearsal snapshot), and
   an install/configuration journal (what you installed, in what order,
   and which evidence drove each choice).
6. **Friction and bounds:** Inject at least one friction condition (auth
   mismatch, wrong destination identity, service down, rejected content
   type, disk/permission fail). Vary at least one bound (product/build
   assumption, listen port, TLS vs cleartext, payload size). Record
   predicted vs observed. Tag TTPs with ATT&CK IDs.
7. **AAR:** Update the plan — sequencing, prerequisites, TTP choice, and
   the **effectiveness envelope**. Explain compromises so a reader cannot
   treat a lean green result as proof against every plausible adversary
   receiver configuration.

## Deliverables

Submit to the instructor:

1. **Evidence-to-build decision record** — recovered clues, source of each
   clue, keep/cut list with plan-linked justification, and explicit gaps
   plus any substitutes you derived.
2. **Network diagram** — roles and addresses in your `/29`.
3. **Host / role / RAM table** — powered-on memory totaling ≤ ~50 GB.
4. **Snapshot plan** — names and purpose.
5. **Install / configuration journal** — ordered build steps tied to
   evidence (not a vendor tutorial dump).
6. **SOM rehearsal script** — client-side steps executed, ATT&CK tags,
   values retargeted, friction inject, and at least one bound/limit test.
7. **Rehearsal after-action** — predicted vs observed; proof that a file
   landed (what you saw and where); plan deltas; **context and
   compromises**.

## Success Criteria

- Every powered-on VM has a plan-linked rationale (no vanity hosts).
- Concurrent RAM stays within the ~50 GB pool limit.
- All static addresses are inside the assigned upper-half block.
- Rehearsal uses the **captured-client upload path** (not a shortcut copy
  onto the receiver).
- At least one successful land is evidenced on the receiver **you** built.
- Recovered original-range destinations were **not** left as the live
  target; retargeting is documented.
- Rehearsal includes at least one friction inject, one limits/bounds test,
  and a written plan delta.
- Compromises and evidence gaps are documented so results can be
  interpreted in context.
- Doctrine terms (SOM, CG/CV, reconnoiter / later degrade-disrupt intent)
  and MITRE ATT&CK tags appear together in the rehearsal product.

## Tie-Back

- **Week 1 / Week 3 group activities:** Your collected client, IOCs, and
  on-target notes are the only student-facing specification for what to
  rebuild.
- **Week 1 planning:** METT-TC → EMLCOA → CG/CV → SOM → rehearsal
  discipline.
- **MITRE ATT&CK:** Technique tags on collection, exfiltration, and the
  receive-side TTPs you rehearsed.
- **MITRE ENGAGE / D3FEND:** Partner-facing labels for blue-space
  implications of friction you observed (for example, file inspection or
  authentication failure).
