# DGX Spark Team Buildout
## Instructor Answer Key (Instructor Only)

Use this as a live walkthrough and grading guide. The goal is not model
eloquence. The goal is to confirm that a team can turn a factory-fresh DGX Spark
into a team-shared AI service: initial system setup, a working local supply chain
(DNS, CA, registry, model mirror), staged buildout with verification at each
layer, real TLS via the lab CA, a unified gateway, automatic model discovery in
the UI, and a controlled external model.

This key is fully copy-pasteable end to end. It assumes the instructor support
stack from [L1.7b Instructor Setup Guide.md](L1.7b%20Instructor%20Setup%20Guide.md)
is already up and preloaded. Students have **no repo access** - they create
`~/stack` and grow Compose/config from
[L1.7b Student Step-by-Step Guide.md](L1.7b%20Student%20Step-by-Step%20Guide.md).
The [stack/](stack/) directory in this lab folder is an instructor reference of
the final end-state only.

## 0. Instructor Pre-Class Checklist

1. Traefik stack up (`step-ca`, `trust`, `technitium`, `traefik`) and mirrors stack up
   (`registry`, `models`) per the Instructor Setup Guide.
2. Registry preloaded (`curl -s https://registry.cso.ops/v2/_catalog` lists the
   required lab images: traefik, vllm, litellm, open-webui; extras are fine).
3. Models warmed on the mirror (`MODEL_1_NAME`, `MODEL_2_NAME`).
4. CA download live: `http://trust.cso.ops/root_ca.crt` and matching
   `root_ca.fingerprint` (trust portal serves both after step-ca init).
5. Classroom DNS points every host at `INFRA_IP`; team zones seeded
   (`seed-team-dns.sh`).
6. Per-team domain + DGX IP assigned (teams 1-5).
7. One `genai.mil` token per team staged for Stage 7, with a token-to-team roster
   that does not record full tokens; revoke/rotate after class.

Suggested board values (per team; example is Team 1). `LAB_BASE_DOMAIN` must equal
the instructor Traefik/mirrors `BASE_DOMAIN` (worked example: `cso.ops`):

```text
LAB_BASE_DOMAIN=cso.ops
TEAM_DOMAIN=team1.cso.ops
DGX_IP=172.16.44.11
INFRA_IP=172.16.44.10
CA_HOST=ca.cso.ops   TRUST_HOST=trust.cso.ops
REGISTRY_HOST=registry.cso.ops   MODELS_HOST=models.cso.ops
GENAI_BASE_URL=<approved genai.mil OpenAI-compatible base, usually ending in /v1>
GENAI_MODEL=<approved Gemini Enterprise model id>
```

Do not write tokens or `LITELLM_MASTER_KEY` values on the board.

## 1. Access and Environment Model

- **Primary access:** SSH from the team workstation to the DGX. All build and
  `docker compose` commands run on the DGX.
- **Fallback:** DGX console if SSH is unavailable.
- **Browser:** the workstation reaches `https://chat|litellm|traefik.<team>.cso.ops`.
- **Supply chain:** DNS + CA + registry + model mirror from the instructor host;
  only the Stage 7 `genai.mil` model is external.

Environment enablement is: lab DNS resolving the team + infra names, the lab root
CA installed on the DGX and workstation, the local registry/mirror reachable, and
the DGX GPU/runtime ready.

## 2. Initial Situational-Awareness Baseline (on the DGX)

Have the team run this after SSHing in, before changing anything. It establishes
time, host identity, user/session, shell, OS/runtime, GPU, key env, processes, and
sockets, and it is your troubleshooting starting point.

```bash
date -Is                                   # remote time (ISO-8601)
timedatectl 2>/dev/null | head -n 3        # timezone / sync state
hostname; hostnamectl 2>/dev/null | head -n 6
whoami; id                                 # user + group context
who; w                                     # active sessions
echo "$SHELL"; bash --version | head -n 1  # interpreter context
uname -a                                   # kernel + arch (expect aarch64 on DGX Spark)
cat /etc/os-release                        # OS/runtime version
nvidia-smi                                 # GPU + driver
docker version; docker compose version
env | sort | grep -Ei 'proxy|hf_|http_' || echo "(no proxy/hf env set)"
ps aux --sort=-%cpu | head -n 12           # top processes
ss -tulpn                                  # listening TCP+UDP sockets
ss -tan state established | head -n 20     # established TCP
```

First-use command notes:

- `ss -tulpn`: `-t` TCP, `-u` UDP, `-l` listening, `-p` process, `-n` numeric -
  the socket picture before any lab service is up.
- `nvidia-smi`: NVIDIA System Management Interface; confirms the GPU is visible to
  the OS, which every vLLM stage depends on.

Expected findings:

- `uname -a` reports `aarch64` (DGX Spark is ARM64).
- `nvidia-smi` shows the GPU and a driver/CUDA version.
- Before the build, no listeners on `8001`, `8002`, `4000`, `3000`, `80`, `443`.
- After the build, `80`/`443` (Traefik) are public; `8001`/`8002`/`4000`/`3000`
  are bound to `127.0.0.1` only.

Teaching point: this baseline lets you prove that app ports stay on loopback and
that only Traefik is exposed - a core security property of the stack.

## 5. Recommended Instructor Walkthrough (Copy-Paste)

Set working variables on the DGX (use the team's real master key):

```bash
export TEAM_DOMAIN=team1.cso.ops
export DGX_IP=172.16.44.11
export INFRA_IP=172.16.44.10
export MASTER_KEY='sk-replace-with-team-key'
```

### 5.1 Stage 1 - Initial DGX setup

Point the box at lab DNS. Quick (runtime) form with `systemd-resolved`:

```bash
IFACE=$(ip route show default | awk '{print $5; exit}')
sudo resolvectl dns "$IFACE" "$INFRA_IP"
sudo resolvectl domain "$IFACE" '~cso.ops'
resolvectl status "$IFACE" | sed -n '1,12p'
```

`resolvectl domain ~cso.ops` routes `*.cso.ops` lookups to the lab resolver. For a
persistent change, set the resolver in the interface's netplan YAML and
`sudo netplan apply`. Verify resolution:

```bash
nslookup chat.$TEAM_DOMAIN     # -> DGX_IP
nslookup registry.cso.ops       # -> INFRA_IP
```

Expected:

```text
Name:   chat.team1.cso.ops
Address: 172.16.44.11
Name:   registry.cso.ops
Address: 172.16.44.10
```

Pull the lab root CA and published fingerprint from the instructor stack, then
verify they match before installing (`update-ca-certificates` adds a cert in
`/usr/local/share/ca-certificates` to the system trust bundle):

```bash
curl -fsS http://trust.cso.ops/root_ca.crt -o root_ca.crt
curl -fsS http://trust.cso.ops/root_ca.fingerprint -o root_ca.fingerprint
openssl x509 -in root_ca.crt -noout -fingerprint -sha256
cat root_ca.fingerprint   # must match the openssl line above
sudo cp root_ca.crt /usr/local/share/ca-certificates/root_ca.crt
sudo update-ca-certificates
```

Expected: fingerprint lines match; `1 added` in the `update-ca-certificates`
output. Install the same cert on the workstation (Linux: same pull + install;
Windows: pull via browser/`curl.exe`, then `Import-Certificate ... Cert:\LocalMachine\Root`).

Confirm Docker pulls from the local registry over trusted TLS:

```bash
sudo systemctl restart docker
docker pull registry.cso.ops/vllm/vllm-openai:latest
```

Expected: layers pull with no `x509`/TLS error. Create the student workspace
(students have no repo - they build from the guide):

```bash
mkdir -p ~/stack/ca
cp ~/root_ca.crt ~/stack/ca/root_ca.crt
cd ~/stack
# Create .env from the Stage 1d block in the student guide.
# Set BASE_DOMAIN=$TEAM_DOMAIN and LITELLM_MASTER_KEY=$MASTER_KEY
# (Bearer token for every gateway client). Do not create docker-compose.yaml yet.
ls -la ~/stack/ca/root_ca.crt ~/stack/.env
```

### 5.2 Stage 2 - `vllm-primary` + curl

Create `~/stack/docker-compose.yaml` with **only** `vllm-primary` + the `web`
network (Stage 2 block in the student guide). Create cache dirs first. Then:

```bash
mkdir -p ~/stack/vols/hf_cache ~/stack/vols/vllm_cache
cd ~/stack
docker compose config >/dev/null && echo "compose OK"
docker compose up -d vllm-primary
# first start pulls the model from the mirror; health can take several minutes
docker compose logs -f vllm-primary   # Ctrl-C once "Application startup complete"
curl -s http://localhost:8001/health && echo
curl -s http://localhost:8001/v1/models | python3 -m json.tool
```

Expected `/v1/models` excerpt (the id is the raw served model):

```json
{ "data": [ { "id": "nvidia/Qwen3.6-35B-A3B-NVFP4", "object": "model" } ] }
```

One completion:

```bash
curl -s http://localhost:8001/v1/chat/completions -H "Content-Type: application/json" \
  -d '{"model":"nvidia/Qwen3.6-35B-A3B-NVFP4","messages":[{"role":"user","content":"Reply with the single word: online"}]}' \
  | python3 -m json.tool
```

Expected: a `choices[0].message.content` containing `online`. Teaching point: no
auth, no TLS, raw model id - motivation for the gateway and proxy.

### 5.3 Stage 3 - Traefik + Open WebUI

Extend Compose to add `traefik` and `open-webui` (Open WebUI pointed directly at
`vllm-primary` - Stage 3 full file in the student guide). Append
`LITELLM_PORT` / `OPEN_WEBUI_PORT` to `.env`. Create Traefik/Open WebUI dirs
first. Then:

```bash
mkdir -p ~/stack/vols/traefik/certs ~/stack/vols/open-webui
cd ~/stack
docker compose up -d traefik
docker compose logs -f traefik    # watch for "Certificates obtained" for the dashboard host
curl -sI https://traefik.$TEAM_DOMAIN | head -n 1
```

`curl -sI` (`-s` silent, `-I` headers only) should return `HTTP/2 200` with **no**
TLS error - that proves DNS + CA trust + ACME all work. The dashboard is open
(no basic auth) for this lab. Then the UI:

```bash
docker compose up -d open-webui
curl -sI https://chat.$TEAM_DOMAIN | head -n 1
```

Confirm the browser loads `https://chat.$TEAM_DOMAIN` with no warning; create a
lab-only admin account. Compose at this point still has **no** `litellm-gateway`.

### 5.4 Stage 4 - LiteLLM in front of the primary

Create `~/stack/litellm-config.yaml` with **only** the primary
`qwen-35b-agent` entry. Add the `litellm-gateway` service block to Compose
(depends on `vllm-primary` only). Then:

```bash
cd ~/stack
docker compose up -d litellm-gateway
curl -s https://litellm.$TEAM_DOMAIN/v1/models -H "Authorization: Bearer $MASTER_KEY" | python3 -m json.tool
```

Expected:

```json
{ "data": [ { "id": "qwen-35b-agent", "object": "model" } ] }
```

Completion through the gateway:

```bash
curl -s https://litellm.$TEAM_DOMAIN/v1/chat/completions -H "Authorization: Bearer $MASTER_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"qwen-35b-agent","messages":[{"role":"user","content":"Reply with: gateway-online"}]}' \
  | python3 -m json.tool
```

### 5.5 Stage 5 - Point Open WebUI at LiteLLM

Edit the `open-webui` service in Compose: `depends_on: litellm-gateway`,
`OPENAI_API_BASE_URL=http://litellm-gateway:4000/v1`, and
`OPENAI_API_KEY=${LITELLM_MASTER_KEY}`. Recreate:

```bash
cd ~/stack
docker compose up -d open-webui
docker compose exec open-webui printenv OPENAI_API_BASE_URL
```

Expected: `http://litellm-gateway:4000/v1`. In the browser, `qwen-35b-agent` is the
selectable model and chat still works - now through the authenticated gateway.

### 5.6 Stage 6 - Secondary model + automatic UI update

Append `MODEL_2_*` / `VLLM_2_*` to `.env`. Add the `vllm-secondary` service block
to Compose. Then:

```bash
cd ~/stack
docker compose up -d vllm-secondary
docker compose logs -f vllm-secondary
curl -s http://localhost:8002/health && echo
```

Add the `qwen-14b-fast` entry to `litellm-config.yaml`
(`api_base: http://vllm-secondary:8000/v1`), then reload and verify:

```bash
docker compose restart litellm-gateway
curl -s https://litellm.$TEAM_DOMAIN/v1/models -H "Authorization: Bearer $MASTER_KEY" | python3 -m json.tool
```

Expected two ids: `qwen-35b-agent` and `qwen-14b-fast`. In Open WebUI, refresh the
model selector - the new model appears with no change to Open WebUI itself.

How students know this happens: Open WebUI queries the gateway's `/v1/models` at
request time rather than holding a static list. This is the "the client updates
itself automatically" demonstration. (In the L1.7a workstation lab the auto-listing
client was Ollama's UI; here Open WebUI plays that role against LiteLLM.)

### 5.7 Stage 7 - External `genai.mil` Gemini Enterprise model

Distribute one token per team through the approved channel. The team appends
`GENAI_BASE_URL`, `GENAI_MODEL`, `GENAI_API_KEY` to `.env`, adds the
`gemini-enterprise` block to `litellm-config.yaml` (setting the model id after
`openai/` to the `genai.mil` model name), adds `GENAI_*` to the
`litellm-gateway` environment in Compose, then:

```bash
cd ~/stack
docker compose up -d litellm-gateway   # recreate so new GENAI_* env is read
curl -s https://litellm.$TEAM_DOMAIN/v1/models -H "Authorization: Bearer $MASTER_KEY" | python3 -m json.tool
```

Expected three ids including `gemini-enterprise`. A completion to
`gemini-enterprise` returns an answer (this call leaves the lab; keep prompts
lab-safe). Confirm all three appear in Open WebUI.

Do not grade exact language. Grade: three models listed, external call succeeds,
token never printed or committed.

## 7. Common Mistakes

- **DNS not persistent:** runtime `resolvectl` works until reboot; a reboot loses
  it if netplan was not updated.
- **Trusting the CA before verifying the fingerprint.** Always compare the local
  `openssl` fingerprint to the published `root_ca.fingerprint` from
  `http://trust.cso.ops/`.
- **Docker not restarted after CA install:** pulls keep failing with `x509` until
  `systemctl restart docker`.
- **Leaving `LITELLM_MASTER_KEY=sk-change-me`.** Change it; every gateway client
  authenticates with that Bearer token.
- **Wildcard vs per-service cert confusion:** this lab issues per-service certs via
  TLS-ALPN-01; wildcard DNS is only for name resolution.
- **Editing `litellm-config.yaml` without reloading** the gateway.
- **Adding later-stage services early** (e.g. LiteLLM or `vllm-secondary` in the
  Stage 2 compose). Grow Compose only with services the current stage configures.
- **Token printed** in a log/screenshot at Stage 7.

## 8. Troubleshooting and Confirmation

### Name does not resolve
```bash
resolvectl status | sed -n '1,15p'
nslookup chat.$TEAM_DOMAIN $INFRA_IP
```
Fix the resolver (Stage 1a). Confirm Technitium on the instructor host has the
right `TEAMn_IP` (re-run `mirrors/scripts/seed-team-dns.sh` or edit the zone).

### `x509`/TLS error on pull or in the browser
```bash
trust list | grep -i "AI Lab" || true
openssl s_client -connect registry.cso.ops:443 -servername registry.cso.ops </dev/null 2>/dev/null | openssl x509 -noout -issuer
```
The issuer should be the lab CA. If not trusted, re-run Stage 1b and restart Docker.

### Traefik does not obtain a certificate
```bash
docker compose logs traefik | grep -i acme | tail -n 20
```
Usual causes: hostname does not resolve to this DGX, CA unreachable
(`curl -sI https://ca.cso.ops:9000/acme/acme/directory`), or `LEGO_CA_CERTIFICATES`
not mounted. Confirm `stack/ca/root_ca.crt` exists and `LAB_ROOT_CA` points at it.

### vLLM not healthy
```bash
docker compose logs vllm-primary | tail -n 40
nvidia-smi
```
Model id not on the mirror (confirm `MODEL_1_NAME`), GPU memory
(`VLLM_1_GPU_MEM_UTIL`), or a still-running first download.

### LiteLLM errors
```bash
docker compose logs litellm-gateway | tail -n 30
curl -s https://litellm.$TEAM_DOMAIN/v1/models -H "Authorization: Bearer $MASTER_KEY"
```
`401` wrong master key; `404` model missing from config or gateway not reloaded;
Stage 7 failures usually mean bad `GENAI_*` values or an expired token.

### Open WebUI shows no models
```bash
docker compose exec open-webui printenv OPENAI_API_BASE_URL
```
Must be `http://litellm-gateway:4000/v1` after Stage 5; confirm the gateway answers
`/v1/models`.

## 10. Acceptable Student Answers

For the automatic-update explanation, acceptable themes:

- Open WebUI reads the model list from the gateway's `/v1/models` dynamically, so
  adding a model at LiteLLM propagates to every client without a UI change.
- The gateway is the single control point for models, auth, and (later) routing/logging.

For the CPT reflection, acceptable themes:

- Team-shared inference gives one governed endpoint, shared models, real TLS, and a
  closed-network supply chain versus a per-analyst workstation stack.
- New risks: CA/trust management, a shared secret (`LITELLM_MASTER_KEY`), single
  point of failure/availability, and data governance for the external model.

Weak answers: claim the UI "auto-detects" models by magic; ignore where the token
goes at Stage 7; leave app ports publicly bound; cannot explain the request path.
