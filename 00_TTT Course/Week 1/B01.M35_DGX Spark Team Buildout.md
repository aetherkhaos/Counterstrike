# DGX Spark Team Buildout - Student Guide
## Student Guide

The DGX is already running. This is a group exercise on that one box. **Each student** means that student, on that student's workstation and Open WebUI account. **Once for the team** means one person does it, and the rest of the team uses the result.

Read the Moodle page [DGX Spark team access](https://moodle.cso.ops/mod/page/view.php?id=5655) for your team. It has the HTTPS names, the LiteLLM, Hermes, OpenClaw, and n8n logins, and the cloud model base URL, model id, and key. Redact those secrets in the packet.

Workstations, ESXi guest VMs, and the DGX boxes are on `172.16.44.0/23`. They reach each other directly.

## 1. Trust the classroom root and open the box

**Each student.** Install the classroom root on your workstation, then confirm the chat and LiteLLM pages for your team domain load.

On the workstation, open `[http://trust.cso.ops](http://trust.cso.ops)`. That page is HTTP on purpose. Download `root_ca.crt`.

Check the fingerprint before you install. These two values must match:

```
curl -fsS http://trust.cso.ops/root_ca.crt -o root_ca.crt
curl -fsS http://trust.cso.ops/root_ca.fingerprint
openssl x509 -in root_ca.crt -noout -fingerprint -sha256
```

`curl -fsS` downloads a URL and fails on an HTTP error. `openssl x509 -fingerprint` prints the SHA-256 fingerprint of the file you just saved. If the two fingerprints differ, stop and tell the instructor.

Install the root the way `[http://trust.cso.ops](http://trust.cso.ops)` describes for your workstation, then restart the browser.

Open `https://chat.<team-domain>/` and `https://litellm.<team-domain>/`. Replace `<team-domain>` from the access page. Both pages must load. A certificate warning after this install is a fault. Stop and tell the instructor.

## 2. List models from the workstation

**Each student.** Ask the gateway which models it is serving, and pick two small local chat models from the parameter count in each id.

`curl` is the HTTP client. The workstation trusts the classroom root, so certificate verification should succeed. The `Authorization` header is the LiteLLM key from the access page.

```
curl -sS https://litellm.<team-domain>/v1/models \
  -H "Authorization: Bearer <LITELLM_KEY>"
```

`-s` hides the progress meter. `-S` still prints an error if the request fails.

Replace `<team-domain>` and the key from the access page. Save the JSON with the key redacted. Local models are the ids that start with `ollama/`.

The number before `b` in the tag is the parameter count, in billions. `ollama/qwen3.5:4b` is 4 billion. `4b` and `8b` are the small chat models. A tag with two sizes, such as `35b-a3b`, gives the total and then the active size (`a3b` is 3 billion active). `e4b` means an effective 4 billion. An id that contains `embedding` is for vectors, not this chat comparison. Mark two small chat ids. Those are the two models you compare.

## 3. Point Open WebUI at LiteLLM and compare two models

**Once for the team,** create the accounts and point Open WebUI at LiteLLM. **Each student** then sends the same prompt to the two small local models and records how the answers differ.

Open `https://chat.<team-domain>/` in the workstation browser.

The first person to sign up becomes the Open WebUI admin, and that signup closes new signups. Create that admin account. It is not the LiteLLM key. In Admin Panel, open Users and choose Add User. Create one account for each teammate, with role user. Give each student the name, email, and password for that account.

Then open Settings, Connections (Admin Settings on this Open WebUI). Turn on the OpenAI-compatible API. Set the base URL to `https://litellm.<team-domain>/v1` and the key to the LiteLLM key from the access page. Save, and refresh the model list.

Each student signs in with the account the admin created. Ask the same short lab-safe prompt of the two small chat models you marked. Write down how the answers differ. If a reply is slow or fails, stop and tell the instructor.

## 4. Try several other local models

**Each student.** Ask that same prompt of several other local chat models, and record what each one does.

In Open WebUI, pick other `ollama/` chat ids from your `/v1/models` list, including at least one whose parameter count is larger than the two you marked. Ask the same prompt of each. Record what each one did: a reply, a slower reply, or a failure.

## 5. Add the cloud model

**Once for the team,** add the cloud model listed on the access page. **Each student** shows that Open WebUI can use it beside the local models.

Open `https://litellm.<team-domain>/`. Sign in as the LiteLLM admin user on the access page. The password is the LiteLLM key on that page.

Add a model in the admin UI. Use the cloud base URL, model id, and key on the access page. The provider is an OpenAI-compatible endpoint. Put the key in the key field of that form.

The gateway stores that model. Each student returns to Open WebUI, refreshes the model list, selects the new name, and asks the same prompt. Save evidence that it answered. Redact the key.

**Notice.** Your team server is up. For the rest of the course, every SI query goes through your team's interface: Open WebUI on your DGX, or Hermes or OpenClaw when you use those. Select the cloud model from the access page in that interface.

## 6. Let the model write a file

**Once for the team.** Let the model do something. The earlier steps only produced answers in a chat. This step makes it call a tool and write a file on the workstation that is running the filesystem server.

Run the tool server on the workstation, not on the DGX. LiteLLM will open a connection to the workstation address. That works because both hosts are on `172.16.44.0/23`.

On the workstation, confirm Node is available and note the home directory and the address on `172.16.44.0/23`:

```
node --version
echo "$HOME"
ip -4 addr
```

`npx` downloads and runs a package. This command starts a filesystem server rooted at your home directory and publishes it with Server-Sent Events so LiteLLM can reach it. `--host 0.0.0.0` listens on the workstation interfaces, not only on loopback. Leave the process running.

```
npx -y supergateway \
  --stdio "npx -y @modelcontextprotocol/server-filesystem $HOME" \
  --port 8000 --host 0.0.0.0 --ssePath /sse --messagePath /message
```

If the DGX cannot connect, the workstation firewall is the usual cause. Allow TCP 8000 from the address that `chat.<team-domain>` resolves to, then retry.

One teammate starts this server and registers it. The poem is written on that workstation. A second registration under the name `filesystem` replaces the team's server.

In the LiteLLM admin UI, add an MCP server:

- Name: `filesystem`
- URL: `http://<workstation-address>:8000/sse`
- Transport: `sse`

Use the workstation address you just recorded, not `localhost`. `localhost` from the gateway is the DGX, not your workstation.

The first Open WebUI account is the admin. Open Settings, then Integrations. Add a connection:

- Name: `LiteLLM`
- Type: MCP (Streamable HTTP)
- URL: `https://litellm.<team-domain>/mcp/`
- Auth: Bearer
- Key: the LiteLLM key from the access page
- Visibility: Public

Save. In a chat, turn on the LiteLLM tool. Ask a small model to draft a short poem and save it as `poem.txt` with the filesystem tool. Then on the workstation:

```
ls -l "$HOME/poem.txt"
```

The file should be there. If the chat replies and the file is missing, stop and tell the instructor.

## 7. Bonus: Hermes, OpenClaw, and a workstation instance

**Once for the team,** sign in to Hermes and OpenClaw on the DGX and try one starter. **Each student** then runs Open WebUI, Hermes, or OpenClaw on that student's workstation and points it at LiteLLM. This step is not required for the packet.

- Hermes: `https://hermes.<team-domain>/`. Sign in with the Hermes user and password on the access page. Send one lab-safe prompt. Confirm a reply.
- OpenClaw: `https://openclaw.<team-domain>/`. The page stays closed until you use the gateway token from the access page. Send one lab-safe prompt. Confirm a reply.

Then pick one starter and give it that job as the first message. Send one lab-safe input. You still decide what to keep.

- **Brief writer.** Paste the local model ids you tried and what each one did. Ask for a three-line situation note.
- **Difference checker.** Paste the two answers from step 3. Ask for one concrete difference.
- **Checklist maker.** Ask for a short ordered checklist of the file-write you just did. Run any command yourself on the workstation.

**Each student.** On your workstation, start one of the three below. Point it at `https://litellm.<team-domain>/v1` with the LiteLLM key from the access page, and use `ollama/qwen3.8:27b`. The container has to trust the classroom root you installed in step 1, so mount the workstation CA bundle. If `docker` is missing, stop and tell the instructor.

Open WebUI listens on `[http://127.0.0.1:3000](http://127.0.0.1:3000)`. The first account on this copy is yours. If the model list is empty, set the same URL and key under Settings, Connections. Select `ollama/qwen3.8:27b` for the prompt.

```
docker run -d --name open-webui \
  -p 127.0.0.1:3000:8080 \
  -v "$HOME/open-webui:/app/backend/data" \
  -v /etc/ssl/certs/ca-certificates.crt:/etc/ssl/certs/ca-certificates.crt:ro \
  -e SSL_CERT_FILE=/etc/ssl/certs/ca-certificates.crt \
  -e REQUESTS_CA_BUNDLE=/etc/ssl/certs/ca-certificates.crt \
  -e OPENAI_API_BASE_URL="https://litellm.<team-domain>/v1" \
  -e OPENAI_API_KEY="<LITELLM_KEY>" \
  ghcr.io/open-webui/open-webui:main
```

Hermes uses the same model fields as the team stack, with the public LiteLLM URL. Build the image, hash a password you choose, and write `$HOME/hermes-config/config.yaml` before you start it. Create that directory first with `mkdir -p "$HOME/hermes-config"`. Open `[http://127.0.0.1:9119](http://127.0.0.1:9119)` and sign in with that username and password.

```

docker run --rm --entrypoint python3 \
```


OpenClaw uses the same provider block as the team stack, with the public LiteLLM URL. Create the directory with `mkdir -p "$HOME/openclaw-config"` and write `$HOME/openclaw-config/openclaw.json`, then open `[http://127.0.0.1:18789](http://127.0.0.1:18789)` and enter the token you chose.


Send one lab-safe prompt. Confirm a reply from `ollama/qwen3.8:27b`. Redact the key.

## Troubleshooting

### The access page still says `change-me`

Stop and tell the instructor. Range support has not published the live values.

### Browser certificate warning

The root is missing, or the browser was not restarted, or Firefox still needs the import on `[http://trust.cso.ops](http://trust.cso.ops)`.

### `/v1/models` returns 401

The bearer token does not match the LiteLLM key on the access page.

### `/v1/models` fails certificate verification

The workstation does not trust the classroom root yet. Repeat step 1.

### Open WebUI has no models

The OpenAI connection must be `https://litellm.<team-domain>/v1` plus that same key. Refresh after saving.

### A model will not answer

Stop and tell the instructor.

### The poem file never appears

Confirm the MCP process is still running, the URL uses the workstation address on `172.16.44.0/23`, and the workstation firewall allows TCP 8000 from the address that `chat.<team-domain>` resolves to. Then tell the instructor.

# DGX Spark Team Buildout — Instructor Answer Key

## Objective and starting context

Students arrive at a workstation. The team DGX already runs the stack. Each student installs the classroom root and lists models from that workstation. The first Open WebUI signup is the admin and closes further signup; that admin creates one user account per student, then points Open WebUI at LiteLLM. Each student compares small local chat models on that account. One person adds the cloud model and registers one filesystem MCP server. The poem is written on that workstation. Hermes and OpenClaw on the DGX are the start of the bonus. Each student who continues runs Open WebUI, Hermes, or OpenClaw on a workstation pointed at `https://litellm.<team-domain>/v1`. They do not build the team Compose and they do not SSH to the DGX.

Values come from the Moodle page [DGX Spark team access](https://moodle.cso.ops/mod/page/view.php?id=5655), including the cloud model base URL, model id, and key. Students choose the two small chat models from the parameter count in the `/v1/models` ids. Do not read secrets aloud. Facilitation is in B01.M35 instructor materials in Lesson Plans and Instructor Slides.zip.

## 2. Initial situational-awareness baseline (on the workstation)

Run this on the workstation before the team changes Open WebUI or LiteLLM. It fixes time, identity, and which host they are on, then proves the team gateway answers with the classroom root.

```
date -Is
hostname
whoami
pwd
curl -fsS http://trust.cso.ops/root_ca.crt -o /tmp/root_ca.crt
curl -fsS http://trust.cso.ops/root_ca.fingerprint
openssl x509 -in /tmp/root_ca.crt -noout -fingerprint -sha256
curl -sS -o /dev/null -w 'chat %{http_code}\n' https://chat.<team-domain>/
curl -sS -o /dev/null -w 'litellm %{http_code}\n' https://litellm.<team-domain>/ui
```

`date -Is` prints the workstation clock in ISO-8601. `hostname` and `whoami` must be the workstation, not the DGX. `pwd` is the directory they will write the poem from later. The two fingerprint lines must match before anyone installs the root. `curl -sS -o /dev/null -w` prints only the HTTP status. A certificate error here means the root is not in the workstation trust store yet. Do not add `-k`.

Why it matters: later failures get blamed on the wrong host when this baseline was skipped. GPU health is a range-support check on the DGX before class. Students do not run `nvidia-smi`.

## 5. Instructor live walkthrough

### 5.1 Root and the two pages

`curl -fsS` fails the command if the download is an HTTP error, so a partial file is not treated as the root. `openssl x509 -noout -fingerprint -sha256` prints one line. It must equal the fingerprint URL.

After the install the trust portal describes, both team URLs must complete TLS verification. `curl` without `-k` is the check. A warning in the browser is the same fault.

### 5.2 Workstation model list

The bearer token is the LiteLLM key. Do not show it.

```
curl -sS https://litellm.<team-domain>/v1/models \
  -H "Authorization: Bearer <LITELLM_KEY>"
```

Expect HTTP 200 and `ollama/<tag>` ids. The two small chat tags are the ones whose count is `4b` or `8b`. A 401 means the wrong key. A local model is any id with the `ollama/` prefix. The cloud model is absent until step 5.5 adds it.

### 5.3 Open WebUI

First signup becomes the local admin and sets signup closed. In Admin Panel, Users, Add User, that admin creates one role-user account per teammate. Then in Settings, Connections, set the OpenAI-compatible URL to `https://litellm.<team-domain>/v1` and the same key. The model dropdown should fill from `/v1/models`.

Each student signs in with the account created for them. Ask one shared prompt of the two small models. Accept any concrete difference (length, wording, refusal, or format). The packet includes each student's comparison, not one comparison for the team.

### 5.4 Third local model

Pick one `ollama/` id that is not in the small pair. The same prompt should return text, more slowly, or fail. Either observation is the evidence. Students stop on a failure.

If you want a live GPU picture, SSH with the instructor key and run `nvidia-smi` while they send the prompt. Project that screen. Do not hand them the key. A stuck large model is unloaded from that login, not by the team.

### 5.5 Cloud model

LiteLLM admin login is user `admin` and the LiteLLM key. Add an OpenAI-compatible model with the base URL, model id, and key from the access page. Do not assume a provider name that is not on that page. The UI stores it because the gateway is configured to keep models in its database.

Each student refreshes Open WebUI and selects that name. A short lab-safe prompt must return text on that student's account. The packet must not contain the key.

Read the notice at the end of student-guide step 5. From here, course SI queries go through the team's Open WebUI, Hermes, or OpenClaw. The access-page cloud model is allowed only when selected in that interface.

### 5.6 Filesystem MCP

On the workstation, `node --version` must succeed. `echo "$HOME"` is the directory the tool may write. `ip -4 addr` must show an address in `172.16.44.0/23`.

`npx -y` runs the package without a prior install. `supergateway` wraps the stdio filesystem server and serves SSE on port 8000 on all interfaces, so the DGX can connect. Leave it in the foreground.

```
npx -y supergateway \
  --stdio "npx -y @modelcontextprotocol/server-filesystem $HOME" \
  --port 8000 --host 0.0.0.0 --ssePath /sse --messagePath /message
```

In LiteLLM admin, add MCP server name `filesystem`, URL `http://<workstation-ip>:8000/sse`, transport `sse`. Not `localhost`.

Open WebUI does not call that SSE URL itself. The Open WebUI admin adds the connection under Settings, Integrations: name `LiteLLM`, type MCP (Streamable HTTP), URL `https://litellm.<team-domain>/mcp/`, bearer auth with the LiteLLM key, Visibility Public. Open WebUI then calls that streamable HTTP endpoint, and the gateway forwards `filesystem-write_file` to the workstation.

The file lands on the workstation whose SSE URL is registered. The name `filesystem` is one server. Another registration under that name replaces it, so the team writes to one workstation at a time. Distinct names remain separate tools on the same LiteLLM key, and every chat that turns on LiteLLM can call any of them. This shared chat does not bind a student to that student's workstation.

If the DGX cannot open TCP 8000, allow that port from the DGX address on the workstation firewall and retry.

One teammate starts the server and registers the name `filesystem`. Another registration under that name replaces it. Students stop and tell you if the chat replies and the file is missing. This curl is the instructor check that the gateway can call the tool:

`GET /v1/mcp/tools` lists tools after registration. Use the write tool name from that list. The filesystem server's write arguments are `path` and `content`. If the list names them differently, use the list.

```
curl -sS https://litellm.<team-domain>/v1/mcp/tools \
  -H "Authorization: Bearer <LITELLM_KEY>"

curl -sS https://litellm.<team-domain>/mcp-rest/tools/call \
  -H "Authorization: Bearer <LITELLM_KEY>" \
  -H "Content-Type: application/json" \
  -d '{"name":"<write-tool-name>","arguments":{"path":"poem.txt","content":"Lab poem.\n"}}'
```

On the workstation, `ls -l "$HOME/poem.txt"` must show the file. `cat` should show the poem text. That file is the grade evidence.

### 5.7 Bonus

Hermes on the DGX returns a login page, then a reply, using the access-page user and password. OpenClaw on the DGX returns 403 until the gateway token is supplied, then a reply. Both are already configured to call `http://litellm-gateway:4000/v1`. Students leave that URL as it is.

A starter is a first message on those DGX pages. Accept any one of these, or a similar lab-safe job: a three-line brief from the local ids they tried, one difference between two Open WebUI answers, or a checklist of the file-write they still run themselves. A bonus sentence that names the starter and says the reply came back is enough.

Each student who continues the bonus runs one workstation instance from the student guide: Open WebUI on `127.0.0.1:3000`, Hermes on `127.0.0.1:9119`, or OpenClaw on `127.0.0.1:18789`. The provider URL in that instance is `https://litellm.<team-domain>/v1`, and the model is `ollama/qwen3.8:27b`. The container mounts `/etc/ssl/certs/ca-certificates.crt` from the workstation so the classroom root is trusted. Accept a reply from that local page. An empty model list on the personal Open WebUI means the CA mount or `SSL_CERT_FILE` was left off.

## 7. Troubleshooting

- `change-me` on the access page: range support has not published the live values.
- Fingerprint mismatch: do not install that `root_ca.crt`.
- Browser warning after the install: the root is not in that browser's trust store, or the team box is still serving the self-signed file. Do not tell them to click through.
- 401 on `/v1/models`: wrong LiteLLM key.
- Certificate error on `curl`: the root is not installed. Do not add `-k`.
- Empty Open WebUI model list: URL must end in `/v1`.
- Large model fails: unload it from the instructor key. Students do not get that login.
- Poem missing: MCP process still running, URL is the workstation `172.16.44.0/23` address, firewall allows TCP 8000 from the DGX, tool name matches `/v1/mcp/tools`.
- `node` missing on the workstation: range support skipped the workstation Node.js install in the team README. Do not have the team install it.
