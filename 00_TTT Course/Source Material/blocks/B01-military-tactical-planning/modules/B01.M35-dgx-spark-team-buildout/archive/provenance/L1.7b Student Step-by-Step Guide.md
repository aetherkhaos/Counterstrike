# DGX Spark Team Buildout
## Student Step-by-Step Guide

This guide is guided, not copy-paste for every decision. You create every
directory and file yourself from the contents in this guide. Each stage gives
you the **goal**, the **files to create or extend**, **decisions to reason
about**, and exact **verification** commands. Do not start a stage until the
previous one verifies.

Grow the Compose file **only** with services you have reached. At the end of
Stage 2 it should contain `vllm-primary` only; later stages add Traefik, Open
WebUI, LiteLLM, and the second model as you configure them.

Work as a team. Capture the output of each verification step for the packet.

## Stage 1. Initial DGX Setup (DNS, CA Trust, Local Supply Chain)

Goal: make the DGX resolve lab names, trust the lab CA, and pull only from the
classroom registry and model mirror. Then create your working directory and the
`.env` you will grow for the rest of the lab.

### 1a. Point the DGX at lab DNS

Decisions to reason about: which resolver does this box use now, and how do you
change it persistently on this OS? Confirm the change rather than assuming it.

Hints: on DGX OS (Ubuntu), DNS is usually managed by `systemd-resolved` /
`netplan`. Set the resolver to `INFRA_IP` for your active interface.

Verify (both must resolve correctly):

```bash
nslookup chat.$TEAM_DOMAIN        # -> DGX_IP
nslookup registry.cso.ops          # -> INFRA_IP
```

If `chat.$TEAM_DOMAIN` does not resolve to your DGX IP, fix DNS before going on -
ACME and Traefik will not work otherwise.

### 1b. Install and verify the lab root CA

Decisions to reason about: why does the DGX need to trust this CA at all? (Two
reasons - Traefik must trust the ACME server to request certs, and your
workstation browser must trust the certs Traefik serves.)

Hints: pull the lab root CA **and** its published fingerprint from the instructor
trust portal over plain HTTP. Install the cert into the system trust store on
both the DGX and your workstation, and confirm your local fingerprint matches the
published file before you trust it.

```bash
# Pull from the instructor trust portal (lab DNS must resolve trust.cso.ops - Stage 1a).
# If the name is not resolving yet, use http://$INFRA_IP/... with a Host header for
# trust.cso.ops, or a temporary /etc/hosts entry for trust.cso.ops.
curl -fsS http://trust.cso.ops/root_ca.crt -o ~/root_ca.crt
curl -fsS http://trust.cso.ops/root_ca.fingerprint -o ~/root_ca.fingerprint

# Confirm the fingerprint matches the published value FIRST:
openssl x509 -in ~/root_ca.crt -noout -fingerprint -sha256
cat ~/root_ca.fingerprint
# The two lines must match. If they do not, stop and get the instructor.

# Then install into the system trust store (DGX and any Linux workstation):
sudo cp ~/root_ca.crt /usr/local/share/ca-certificates/root_ca.crt
sudo update-ca-certificates
```

On a Windows workstation (admin PowerShell), pull the same files (curl.exe or
browser to `http://trust.cso.ops/`), confirm the fingerprint, then:

```powershell
Import-Certificate -FilePath .\root_ca.crt -CertStoreLocation Cert:\LocalMachine\Root
```

You will copy the CA into your stack directory in Stage 1d (Traefik/lego reads it
from there).

### 1c. Verify Docker can pull from the local registry

Decisions to reason about: the images are served over TLS by `registry.cso.ops`.
Once the system trusts the lab CA and Docker is restarted, pulls should just work.

```bash
sudo systemctl restart docker
docker pull registry.cso.ops/vllm/vllm-openai:latest
```

Expected: the pull succeeds with no TLS/x509 error. If you get a certificate
error, the CA is not trusted yet (revisit 1b). If the name does not resolve,
revisit 1a.

### 1d. Create your stack directory and `.env`

You build the stack under `~/stack` on the DGX. Create the CA directory, place
the cert where Traefik will read it later, and write a `.env` for the services you
are about to add. Create other directories when a later stage needs them. Do
**not** create `docker-compose.yaml` yet - that starts in Stage 2 with only
`vllm-primary`.

```bash

cp ~/root_ca.crt ~/stack/ca/root_ca.crt
```


## Stage 2. Primary Inference: `vllm-primary` + curl

Goal: create your first Compose service - only the primary model server - and
prove it serves inference with a raw HTTP request before any UI exists.

### What is vLLM?

vLLM is an **inference engine**: it loads a large language model onto the GPU and
serves it over an HTTP API that looks like OpenAI's (`/v1/models`,
`/v1/chat/completions`). Think of it as the process that actually runs the model -
not a chat app, not a proxy. Clients send prompts; vLLM returns completions.

In CND terms it is an application service with a clear trust boundary: it holds
valuable compute (GPU) and model weights, speaks a well-known API shape, and by
default has **no authentication**. That is why you will bind it to loopback and
put a gateway and reverse proxy in front of it later. Hugging Face-style model
ids (for example `nvidia/Qwen3.6-...`) are the "packages" it loads; in this lab
those weights come from the classroom mirror via `HF_ENDPOINT`, not the public
internet.

Decisions to reason about: which host port is `vllm-primary` published on, and why
is it bound to loopback? What model id will it actually serve (look at the
`--model` value and `MODEL_1_NAME`)?

Create the cache directories this service needs, then create
`~/stack/docker-compose.yaml` with **only** this content (primary model +
network):

```bash
mkdir -p ~/stack/vols/hf_cache ~/stack/vols/vllm_cache
```

```yaml
# ~/stack/docker-compose.yaml  (end of Stage 2)

services:
  vllm-primary:
    image: ${REGISTRY_PREFIX:-registry.cso.ops/}vllm/vllm-openai:latest
    container_name: vllm-primary
    environment:
      - HF_HOME=/root/.cache/huggingface
      - HF_TOKEN=${HF_TOKEN:-}
      - HF_ENDPOINT=${HF_ENDPOINT:-https://models.cso.ops}
    volumes:
      - ${HUGGINGFACE_CACHE:-./vols/hf_cache}:/root/.cache/huggingface
      - ${VLLM_CACHE:-./vols/vllm_cache}/primary:/root/.cache/vllm
    ports:
      - "127.0.0.1:${VLLM_1_PORT:-8001}:8000"
    ipc: host
    networks:
      - web
    deploy:
      resources:
        reservations:
          devices:
            - driver: nvidia
              count: all
              capabilities: [gpu]
    command: >
      --model ${MODEL_1_NAME:-nvidia/Qwen3.6-35B-A3B-NVFP4}
      --quantization modelopt
      --gpu-memory-utilization ${VLLM_1_GPU_MEM_UTIL:-0.45}
      --max-model-len ${VLLM_1_MAX_MODEL_LEN:-32768}
      --trust-remote-code
      --enable-auto-tool-choice
      --tool-call-parser ${VLLM_1_TOOL_PARSER:-qwen3_coder}
      -cc.cudagraph_mode=PIECEWISE
      -cc.max_cudagraph_capture_size=256
      --safetensors-load-strategy prefetch
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:8000/health"]
      interval: 15s
      timeout: 5s
      retries: 5
      start_period: 600s
    restart: unless-stopped

networks:
  web:
    name: web
```

What each line does:

| Line | Purpose |
| --- | --- |
| `services:` | Starts the service definitions block. |
| `vllm-primary:` | Names this service; other containers reach it as `vllm-primary` on the Docker network. |
| `image: ${REGISTRY_PREFIX:-registry.cso.ops/}vllm/vllm-openai:latest` | Image to run; `${REGISTRY_PREFIX}` comes from `.env` so pulls hit the classroom registry. |
| `container_name: vllm-primary` | Fixed container name for logs and `docker compose` commands. |
| `environment:` | Variables passed into the container. |
| `HF_HOME=/root/.cache/huggingface` | Where Hugging Face caches model files inside the container. |
| `HF_TOKEN=${HF_TOKEN:-}` | Optional token for gated models; empty unless you set `HF_TOKEN` in `.env`. |
| `HF_ENDPOINT=${HF_ENDPOINT:-https://models.cso.ops}` | Sends model downloads to the classroom mirror, not the public internet. |
| `volumes:` | Host paths mounted into the container so caches survive restarts. |
| `${HUGGINGFACE_CACHE:-./vols/hf_cache}:...` | Persists downloaded weights on the DGX under `~/stack/vols/hf_cache`. |
| `${VLLM_CACHE:-./vols/vllm_cache}/primary:...` | Persists vLLM's own cache for this instance. |
| `ports:` | Publishes container ports to the host. |
| `127.0.0.1:${VLLM_1_PORT:-8001}:8000` | Binds the API to loopback only on host port 8001 (or your `VLLM_1_PORT`); not reachable from other hosts. |
| `ipc: host` | Shares host IPC namespace; required for GPU workloads on many setups. |
| `networks: - web` | Attaches the container to the `web` network defined at the bottom of the file. |
| `deploy: ... devices: nvidia` | Requests all NVIDIA GPUs for this container. |
| `command: >` | vLLM startup flags; values after `${...}` are read from `.env`. |
| `--model ${MODEL_1_NAME:-...}` | Which model id vLLM loads from the mirror. |
| `--quantization modelopt` | Uses NVIDIA ModelOpt quantization for this hardware. |
| `--gpu-memory-utilization ...` | Caps GPU memory use so a second model can fit later. |
| `--max-model-len ...` | Maximum context length vLLM will serve. |
| `--trust-remote-code` | Allows model code from the mirror to run (needed for some architectures). |
| `--enable-auto-tool-choice` / `--tool-call-parser ...` | Enables tool-calling support for agent workflows later in the course. |
| `-cc.cudagraph_mode=PIECEWISE` / `-cc.max_cudagraph_capture_size=256` | CUDA graph tuning for throughput on supported GPUs. |
| `--safetensors-load-strategy prefetch` | Loads weights with a prefetch strategy suited to large models. |
| `healthcheck:` | Compose waits for this before marking the service healthy. |
| `test: ["CMD", "curl", "-f", "http://localhost:8000/health"]` | Inside the container, curl the vLLM health endpoint on port 8000. |
| `interval` / `timeout` / `retries` | How often to probe, how long to wait, and how many failures before unhealthy. |
| `start_period: 600s` | Grace period on first start while the model downloads and loads (can take several minutes). |
| `restart: unless-stopped` | Restart the container if it exits, unless you stopped it manually. |
| `networks:` / `web:` / `name: web` | Defines a user-named bridge network all lab services will share. |

Validate and bring it up (first start pulls the model from the mirror and can
take several minutes):

```bash
cd ~/stack
docker compose config >/dev/null && echo "compose OK"
docker compose up -d vllm-primary
docker compose logs -f vllm-primary
```

Verify health, then list the served model, then run one completion:

```bash
curl -s http://localhost:8001/health

curl -s http://localhost:8001/v1/models | python3 -m json.tool

curl -s http://localhost:8001/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
    "model": "'"$(curl -s http://localhost:8001/v1/models | python3 -c 'import sys,json;print(json.load(sys.stdin)["data"][0]["id"])')"'",
    "messages": [{"role":"user","content":"Reply with the single word: online"}]
  }'
```

What to confirm:

- `/health` returns success (empty body, HTTP 200).
- `/v1/models` lists exactly one model - the id vLLM is serving.
- The chat call returns a `choices[0].message.content`.

Teaching point: at this layer the model id is the raw model name, and there is no
auth and no TLS - that is exactly why you will put a gateway and a proxy in front
of it.

## Stage 3. Chat UI: Open WebUI (behind Traefik)

Goal: add Traefik and Open WebUI to your Compose file, publish a browser UI over
HTTPS at your team domain, and confirm the whole DNS + CA + ACME chain works.

### What is Traefik?

Traefik is a **reverse proxy and TLS terminator** - the same role nginx, HAProxy,
or a load balancer plays in front of backend apps. In this lab it:

- Listens on 80/443 (the only ports other hosts should reach on the DGX).
- Discovers routes from Docker labels (which hostname maps to which container).
- Obtains and renews TLS certificates from the lab ACME CA (`step-ca`) using
  TLS-ALPN-01 - the same ACME idea as Let's Encrypt, but against your classroom CA.
- Redirects HTTP to HTTPS and presents the browser with a trusted certificate once
  the workstation trusts the lab root CA.

App containers stay on loopback or the internal Docker network; Traefik is the
edge. If Traefik cannot get a cert, the usual causes are the same ones you see
with any ACME setup: DNS does not point at this host, the CA is unreachable, or
the proxy does not trust the CA that signs the ACME endpoint.

### What is Open WebUI?

Open WebUI is a **browser chat front end** for OpenAI-compatible model APIs. Users
log in, pick a model, and send prompts; the UI turns that into HTTP calls to
whatever backend you configure (`OPENAI_API_BASE_URL`). It does not run the model
itself - it is a client.

In Stage 3 you point it straight at `vllm-primary` so you can prove the UI path
works. That is awkward operationally (raw model names, no shared auth, one backend
only) - which is why Stage 4–5 put LiteLLM between the UI and the models.

### 3a. Add Traefik and prove ACME works

Decisions to reason about: Traefik requests a certificate per service hostname
from the lab CA using the TLS-ALPN-01 challenge. What has to be true for that to
succeed? (DNS resolves your hostname to this DGX; the CA is reachable; Traefik
trusts the CA via `LEGO_CA_CERTIFICATES`.)

Add these lines to `~/stack/.env` (ports for services you are about to add):


`~/stack/docker-compose.yaml` so it contains **vllm-primary, traefik, and
open-webui**. Open WebUI is wired **directly** at `vllm-primary` for this stage -

## Stage 4. Gateway: LiteLLM in front of `vllm-primary`

Goal: add the LiteLLM gateway service and its config file so you have a single
OpenAI-compatible endpoint with one auth key and clean model names.

### What is LiteLLM?

LiteLLM is an **API gateway for LLM backends**. Clients talk to one OpenAI-shaped
endpoint (`/v1/models`, `/v1/chat/completions`); LiteLLM maps a friendly model
name to a real backend (`api_base` + raw model id). In this lab that means
`qwen-35b-agent` -> `http://vllm-primary:8000/v1`, and later more backends on the
same front door.

From a CND perspective it is the control point you put in front of unauthenticated
model servers:

- One place to enforce a shared secret (`LITELLM_MASTER_KEY` as a Bearer token).
- One place to rename and inventory models without changing every client.
- One place to add or remove backends (second GPU model, external API) without
  rebuilding the UI.

It does not replace Traefik (TLS and host routing) and it does not replace vLLM
(actual inference). Traefik publishes `https://litellm.$TEAM_DOMAIN`; LiteLLM
authenticates and routes to the right model service.

**Docker DNS vs host ports:** when LiteLLM (or Open WebUI) calls another container,
it uses that service's **Compose service name** on the shared `web` network and the
**container's internal listen port** - for example `http://vllm-primary:8000/v1`.
That is Docker's built-in DNS: `vllm-primary` resolves to the other container's
IP. Do **not** put `localhost` or `127.0.0.1` in `api_base` here - inside the
LiteLLM container, localhost means LiteLLM itself, not the DGX host and not
vLLM. The host-published ports (`127.0.0.1:8001`, `8002`, `4000`) are only for
you curling from an SSH session on the DGX.

Decisions to reason about: LiteLLM maps a friendly `model_name` to a backend
`model` + `api_base`. For Stage 4 you want **only** the primary entry
(`qwen-35b-agent` -> `http://vllm-primary:8000/v1`).

Create `~/stack/litellm-config.yaml`:

```yaml
# ~/stack/litellm-config.yaml  (end of Stage 4 — primary only)

model_list:
  - model_name: qwen-35b-agent
    litellm_params:
      model: openai/nvidia/Qwen3.6-35B-A3B-NVFP4
      api_base: http://vllm-primary:8000/v1
      api_key: "not-needed"

general_settings:
  master_key: os.environ/LITELLM_MASTER_KEY
```

What each field does:

| Field | Purpose |
| --- | --- |
| `model_name: qwen-35b-agent` | Friendly id clients request (`curl`, Open WebUI). |
| `model: openai/nvidia/Qwen3.6-...` | Backend model id; `openai/` tells LiteLLM to speak OpenAI protocol to that backend. |
| `api_base: http://vllm-primary:8000/v1` | Where LiteLLM reaches vLLM: Compose **service name** + **internal** port 8000 (not `localhost:8001`). |
| `api_key: "not-needed"` | vLLM has no auth; placeholder satisfies the client library. |
| `master_key: os.environ/LITELLM_MASTER_KEY` | Reads the Bearer secret from the container environment (your `.env`). |

Add the `litellm-gateway` service to `~/stack/docker-compose.yaml` (keep
`traefik`, `vllm-primary`, and `open-webui` as they are). Insert this block:

```yaml

      - "127.0.0.1:${LITELLM_PORT:-4000}:4000"

      - web
    restart: unless-stopped
    labels:
      - "traefik.enable=true"
      - "traefik.http.routers.litellm.rule=Host(`${LITELLM_SUBDOMAIN:-litellm}.${BASE_DOMAIN:-team1.cso.ops}`)"
      - "traefik.http.routers.litellm.entrypoints=websecure"
      - "traefik.http.routers.litellm.tls=true"
      - "traefik.http.routers.litellm.tls.certresolver=labca"
      - "traefik.http.services.litellm.loadbalancer.server.port=4000"
```

What each line does:

| Line | Purpose |
| --- | --- |
| `litellm-gateway:` | OpenAI-compatible API gateway in front of your model servers. |
| `image: ...berriai/litellm:main-latest` | LiteLLM image from the classroom registry. |
| `depends_on: vllm-primary: condition: service_healthy` | Waits until the primary model passes its healthcheck before starting. |
| `./litellm-config.yaml:/app/config.yaml:ro` | Mounts your gateway config read-only. |
| `LITELLM_MASTER_KEY=${LITELLM_MASTER_KEY:-sk-change-me}` | Shared Bearer token clients must present to call the gateway. |
| `command: ["--config", "/app/config.yaml", "--port", "4000"]` | Starts LiteLLM with your config on port 4000 inside the container. |
| `127.0.0.1:${LITELLM_PORT:-4000}:4000` | Gateway API on loopback; Traefik publishes it at `litellm.$TEAM_DOMAIN`. |
| `traefik.http.routers.litellm.rule=Host(...)` | HTTPS hostname for the gateway API. |
| `traefik.http.services.litellm.loadbalancer.server.port=4000` | Traefik forwards TLS traffic to LiteLLM's port 4000. |

## Stage 6. Second Model + Automatic UI Update

Goal: add a second model server to Compose, expose it through LiteLLM, and show
the chat UI's model list updating on its own.

### What is `vllm-secondary`?

Same software as `vllm-primary` (vLLM), second process. You run two inference
engines on one GPU host so you can serve different model sizes or roles (here a
heavier "agent" model and a smaller/faster one) without mixing them in a single
vLLM instance. Each gets its own loopback port, GPU memory share, and cache
path; LiteLLM is what presents both under one authenticated API. Clients (Open
WebUI) should not talk to this container directly once the gateway is in place.

### 6a. Add `.env` vars and the secondary service

Append to `~/stack/.env`:

```bash
VLLM_2_MAX_MODEL_LEN=16384
```

Add `vllm-secondary` to `~/stack/docker-compose.yaml` (keep all existing
services). It reuses the same `hf_cache` host directory as the primary instance;
only the vLLM cache path differs:

```yaml
  vllm-secondary:
    image: ${REGISTRY_PREFIX:-registry.cso.ops/}vllm/vllm-openai:latest
    container_name: vllm-secondary
    environment:
      - HF_HOME=/root/.cache/huggingface
      - HF_TOKEN=${HF_TOKEN:-}
      - HF_ENDPOINT=${HF_ENDPOINT:-https://models.cso.ops}
    volumes:
      - ${HUGGINGFACE_CACHE:-./vols/hf_cache}:/root/.cache/huggingface
      - ${VLLM_CACHE:-./vols/vllm_cache}/secondary:/root/.cache/vllm
    ports:
      - "127.0.0.1:${VLLM_2_PORT:-8002}:8000"
    ipc: host
    networks:
      - web
    deploy:
      resources:
        reservations:
          devices:
            - driver: nvidia
              count: all
              capabilities: [gpu]
    depends_on:
      vllm-primary:
        condition: service_healthy
    command: >
      --model ${MODEL_2_NAME:-nvidia/Qwen3.6-27B-NVFP4}
      --quantization modelopt
      --gpu-memory-utilization ${VLLM_2_GPU_MEM_UTIL:-0.30}
      --max-model-len ${VLLM_2_MAX_MODEL_LEN:-16384}
      --trust-remote-code
      --enable-auto-tool-choice
      --tool-call-parser ${VLLM_2_TOOL_PARSER:-qwen3_coder}
      --safetensors-load-strategy prefetch
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:8000/health"]

      timeout: 5s
      retries: 5
      start_period: 600s
    restart: unless-stopped
```

## Troubleshooting Quick Reference

### Browser shows a certificate warning
The workstation does not trust the lab root CA. Re-do Stage 1b on the workstation
(pull cert + fingerprint from `http://trust.cso.ops/`, confirm they match, then
install) and confirm the fingerprint still matches the published file.

### Traefik never gets a certificate
Check `docker compose logs traefik` for the ACME error. Usual causes: your
hostname does not resolve to this DGX (`nslookup chat.$TEAM_DOMAIN`), the CA is
unreachable, or Traefik does not trust the CA (`LAB_ROOT_CA` / `LEGO_CA_CERTIFICATES`).

### `vllm-primary` never becomes healthy
`docker compose logs vllm-primary`. Usual causes: the model id is not cached on the
mirror (confirm `MODEL_1_NAME` with the instructor), GPU memory pressure
(`VLLM_1_GPU_MEM_UTIL`), or a still-in-progress first-time model download.

### Image pull fails
`docker pull registry.cso.ops/vllm/vllm-openai:latest`. TLS error -> CA not trusted
(Stage 1b + `systemctl restart docker`). Name error -> DNS (Stage 1a).

### Open WebUI shows no models
Confirm which backend it points at (`docker compose exec open-webui printenv
OPENAI_API_BASE_URL`) and that that backend answers `/v1/models`. After Stage 5 it
must be `http://litellm-gateway:4000/v1`.

### LiteLLM 401 / 404
`401` -> wrong `LITELLM_MASTER_KEY` in the request. `404` on a model -> the
`model_name` is not in `litellm-config.yaml`, or you did not reload the gateway
after editing it. Connection errors to a backend often mean `api_base` used
`localhost` instead of the Compose service name (for example
`http://vllm-primary:8000/v1`).
